# 03 · 案例研究：USB 桥接器空闲停转杀掉 ATA 自检

这是本项目里最有价值的发现，也是最难自己想到的一个。

## 现象

一块盘装在某个 USB-SATA 桥接盒里（桥接芯片型号从略）。

扩展自检**连续 4 次失败**：

```
Num  Test_Description    Status                  Remaining  LifeTime(hours)  LBA_of_first_error
# 2  Extended offline    Aborted by host               90%      12345         -
# 3  Extended offline    Aborted by host               90%      12342         -
# 4  Extended offline    Aborted by host               90%      12340         -
# 5  Extended offline    Interrupted (host reset)      90%      12340         -
```

关键特征：

1. **全部停在 90%** —— 也就是开头 10% 以内就死，一次没走到 80%
2. **状态码还不一样**：1 次 `host reset`（0x29），3 次 `aborted by host`（0x19）
3. **SMART 层面完全干净**：05/196/197/198 全 0、机械启动失败 0、不可修正错误 0

## 排除过程

| 嫌疑 | 怎么排除的 |
|---|---|
| 坏道 | 所有坏道计数全 0；`LBA_of_first_error` 一直是 `-` |
| Windows 省电 | 全局 USB 选择性暂停 = 禁用；设备级 `PnPCapabilities=24`；睡眠 / 硬盘 / 休眠超时全 = 0 |
| 盘的 APM | `smartctl -g apm` = 128 `minimum power consumption without standby` |
| ATA 待机定时器 | `smartctl -s standby,0` 设成禁用，桥接器回话 `Standby timer set to 0 (disabled)` —— **照样死** |
| USB 链路复位 | `Hardware Resets` / `ASR Events` / `Interface CRC` 三次里两次**一动没动** |
| 断电 | `Power_Cycle_Count` 没动过 |
| Windows 事件日志 | 自检期间**一条相关事件都没有** —— 动手的那一层 OS 根本看不见 |
| 我们的监控查询 | 后续实验证明查询**不是**元凶（见下） |

## 真正的根因

**盘的主轴在被反复停转。**

对比 SMART 计数器：

| 计数 | 空闲状态（回顾）| 说明 |
|---|---|---|
| `04 起停次数` | **数小时内十几次** | **大致每二三十分钟一次** |
| `12 通电次数` | 不变 | **不是断电，是被显式命令停转** |
| `193 磁头加载` | 同量级上升 | 同步上升 |

而 §"ATA 待机定时器"那一行说明：**把盘自己的待机定时器关掉也没用** —— 所以停转命令**来自桥接器固件自己的逻辑**。

桥接器的判定依据是「**USB 上有没有流量**」。而 ATA 自检在**盘内**跑、主机侧**零流量** —— 桥接器看到的就是"这盘闲着"，于是发停转 → **自检被中止**。

对照证据：同一个主机、同样零流量，但换用**另一种桥接芯片**的盒子里那块盘，数小时的自检一次没被打断。**唯一差别是桥接芯片。**

## 解药：持续喂 USB 流量

自检期间每 45 秒发两条 ATA 查询（`smartctl -A` + `smartctl -c`）—— **零写入、零额外磨损**。

### 结果

| | 空闲时 | 自检全程 |
|---|---|---|
| **起停次数** | 数小时内十几次 | **+0**（全程） |
| **Hardware Resets** | — | +0 |
| **ASR Events** | — | +0 |
| **Interface CRC** | — | +0 |
| 结果 | 每二三十分钟被停转打死 | **`Completed without error`**，跑完一整轮整盘读 |

### 顺便回答了一个问题：「查询会不会把自检搞坏？」

**不会，反而它是解药。** 实验设计很干净：

| 尝试 | 待机定时器 | 设备电源管理 | 查询频率 | 结果 |
|---|---|---|---|---|
| 第 4 次 | 已禁用 | 已关 | 少 | **十几分钟内死** |
| 第 5 次 | 已禁用 | 已关 | **每 45 秒** | **跑完整整一轮（数小时）** |

唯一改变的变量就是查询频率。所以既证明了根因是「缺流量」，也排除了「查询是杀手」。

> 按直觉给出的方案是「中途别查，免得打扰它」—— 那只会死第五次。

## 可复用的结论

1. **ATA 自检在主机侧没有 I/O。** 任何「按主机活动判空闲」的中间层都可能把它干掉。
2. **自检期间挂一个定期查询的观察器**，一举两得：既拿到精确到秒的进度记录，又顺手保活。
3. **诊断这类问题的正确指标是 `04 起停次数` 的增量**，不是任何 SMART 健康位。
4. **`SMART overall-health ... PASSED` 和自检能不能跑完，是两件独立的事。**
5. 症状是「自检总在开头 10% 死、且状态码在 0x19 / 0x29 之间变化」时，**优先怀疑中间层在停转**。

## 顺带：这类盒子不值得信任

同一个盒子在同一天还表演了：低电流下的炒豆声（供电欠压）、SCSI 命令透传失败（`unsupported scsi opcode`）、host reset、反复 abort。**桥接器是整条链路里最薄弱也最不被监控的一环。**

长期在线存储建议直连 SATA。USB 桥接的价值是便携，不是 7×24 的可靠性。
